# Dependency Setup

## 1. Objective

Set up and synchronize Python project dependencies using `uv`.

This stage is responsible for:

- Identifying the project's dependency declaration sources.
- Determining whether dependencies need to be installed, synchronized, or migrated.
- Installing dependencies into the correct project environment.
- Maintaining consistency between dependency declarations and lockfiles.
- Verifying that the dependency environment is usable.

The goal is to establish a reproducible dependency environment without unnecessarily modifying existing project configurations.

---

## 2. Prerequisites

Before proceeding, read the following documents:

- `environment-detection.md`
- `project-detection.md`
- `environment-initialization.md`

Use their detection results to determine:

- Project root directory.
- Project management type.
- Python interpreter version.
- Whether `uv` is available.
- Whether a project-local `.venv` exists.
- Existing dependency declaration files.
- Existing lockfiles.

### Mandatory Package Management Rule

Always use `uv` whenever it can perform the required operation.

- Never use `pip install` when an equivalent `uv` command is available.
- Never use `python -m pip` when an equivalent `uv` command is available.
- Prefer `uv add`, `uv sync`, and other uv-native project management commands.
- Do not introduce another package manager unless explicitly required by the project.

A `requirements.txt` file does not automatically mean that pip must be used.

## 3. Dependency Source Detection

Inspect the project root and identify all dependency-related files.

Common files include:

| File | Purpose |
|---|---|
| `pyproject.toml` | Project metadata and dependency declarations |
| `uv.lock` | Locked dependency versions generated by uv |
| `requirements.txt` | Dependency declarations |
| `requirements-dev.txt` | Development dependencies |
| `requirements-test.txt` | Test dependencies |
| `setup.py` | Legacy package configuration |
| `setup.cfg` | Legacy package configuration |
| `Pipfile` | Pipenv dependency configuration |
| `poetry.lock` | Poetry lockfile |
| `pdm.lock` | PDM lockfile |

Do not assume that every detected file is actively used.

Determine which files are authoritative and whether multiple dependency management configurations coexist.

### Dependency Source Priority

Use the following priority when determining the dependency source:

1. Explicit project documentation or user instructions.
2. Existing `pyproject.toml` and its corresponding lockfile.
3. Existing project-specific dependency configuration.
4. Existing requirements files.
5. Dependency information inferred from the source code.

If multiple dependency sources conflict, do not silently choose one.

Report the conflict and determine the intended source before making changes.

## 4. Dependency Setup Strategy

Select the appropriate workflow based on the detected project type.

### 4.1 uv-managed project

Conditions:

- `pyproject.toml` exists.
- The project is managed by uv.
- `uv.lock` may or may not exist.

Actions:

1. Inspect `[project.dependencies]` and optional dependency groups.
2. Inspect `uv.lock`, if available.
3. Determine whether the lockfile is consistent with `pyproject.toml`.
4. Synchronize the environment using `uv sync`.

Standard command:

```bash
uv sync
```

For projects that define development dependencies in dependency groups, use the project's existing configuration.

Do not manually reinstall every package listed in `pyproject.toml`.

Do not regenerate the lockfile unnecessarily.

### 4.2 pyproject.toml without uv.lock

Conditions:

- `pyproject.toml` exists.
- `uv.lock` does not exist.

Actions:

1. Inspect the existing dependency declarations.
2. Preserve the existing project metadata and dependency configuration.
3. Generate the uv lockfile and synchronize dependencies.

Command:

```bash
uv sync
```

This allows uv to resolve dependencies and generate `uv.lock`.

Do not replace the existing `pyproject.toml` with a newly initialized project.

### 4.3 requirements-based project

Conditions:

- `requirements.txt` or other requirements files exist.
- The project does not have an established uv dependency configuration.

Actions:

1. Inspect all requirements files.
2. Identify production and development dependencies.
3. Check for version constraints, editable installations, local paths, Git dependencies, and environment markers.
4. Determine whether the project should migrate to uv-native dependency management.

Preferred approach:

Migrate dependency declarations into `pyproject.toml` when appropriate.

For example:

```bash
uv init --bare
uv add -r requirements.txt
```

If development dependencies are maintained separately:

```bash
uv add --dev -r requirements-dev.txt
```

Important:

- Only initialize project metadata if it does not already exist.
- Do not overwrite existing project configuration.
- Preserve dependency constraints whenever possible.
- Review the generated `pyproject.toml` and `uv.lock`.
- Do not delete original requirements files until migration has been verified and explicitly approved.

If migration is not appropriate, use uv's pip-compatible interface:

```bash
uv pip install -r requirements.txt
```

This is an acceptable fallback because the package operation is still performed through `uv`, not `pip`.

### 4.4 Legacy project

Conditions:

- The project uses legacy dependency configuration such as `setup.py`, `setup.cfg`, or another package manager.
- No established uv-native configuration exists.

Actions:

1. Inspect the existing dependency configuration.
2. Determine whether the project can be safely migrated to uv.
3. Preserve existing installation behavior and dependency constraints.
4. Avoid introducing a new dependency management configuration without understanding the current setup.

If migration is appropriate, establish uv-native configuration.

If migration is not appropriate, use the compatible uv workflow where possible.

Do not force migration simply to standardize the project.

### 4.5 New or empty project

Conditions:

- No existing dependency declarations exist.
- No dependency lockfile exists.

Actions:

1. Confirm that the project has been initialized.
2. Keep the project configuration minimal.
3. Add dependencies only when required by the project.
4. Use `uv add` to manage new dependencies.

Example:

```bash
uv add requests
uv add pandas numpy
uv add --dev pytest ruff
```

Do not install arbitrary packages just because they are commonly used in Python projects.

## 5. Dependency Installation Rules

### 5.1 Use uv-native commands

Use the following commands for common dependency operations:

| Operation | Command |
|---|---|
| Synchronize dependencies | `uv sync` |
| Add a dependency | `uv add <PACKAGE>` |
| Add multiple dependencies | `uv add <PACKAGE_1> <PACKAGE_2>` |
| Add development dependencies | `uv add --dev <PACKAGE>` |
| Remove a dependency | `uv remove <PACKAGE>` |
| Update dependencies | `uv lock --upgrade` |
| Install from requirements file | `uv pip install -r requirements.txt` |

Do not use `pip install` or `python -m pip install` when uv can perform the operation.

### 5.2 Production and development dependencies

Separate dependencies according to their purpose.

**Production dependencies**

Packages required for the application to run.

Example:

```bash
uv add fastapi pydantic
```

**Development dependencies**

Packages used for development, testing, linting, and formatting.

Example:

```bash
uv add --dev pytest ruff mypy
```

Do not classify a package as a development dependency if the production application requires it at runtime.

### 5.3 Optional dependencies

Use optional dependency groups when a package is only needed for a specific feature.

For example:

```toml
[project.optional-dependencies]
visualization = [
    "matplotlib",
    "plotly",
]
```

Install the optional group when needed:

```bash
uv sync --extra visualization
```

Do not install optional dependencies unless the project requires them.

### 5.4 Avoid unnecessary dependency changes

Do not:

- Upgrade all packages without a specific reason.
- Remove packages simply because they appear unused.
- Change version constraints without understanding compatibility.
- Replace an existing lockfile without justification.
- Install packages globally when a project-local environment is available.
- Install dependencies into an unrelated active virtual environment.

## 6. Environment Synchronization

Before synchronizing dependencies, verify that uv is operating on the intended project and environment.

Expected environment:

- Project root: detected project root.
- Virtual environment: project-local `.venv`.
- Python interpreter: selected during Environment Initialization.
- Package manager: uv.

For uv-managed projects, use:

```bash
uv sync
```

If development dependencies are defined in dependency groups, include them in the synchronization process.

For example:

```bash
uv sync --all-groups
```

Do not use `--all-groups` blindly if the project contains groups that are not required for the current workflow.

### Existing environment handling

- Reuse an existing valid `.venv`.
- Do not delete and recreate `.venv` just to perform dependency synchronization.
- Do not install dependencies into the global Python environment.
- If the environment is incompatible or corrupted, report the issue before replacing it.
- Do not silently switch Python interpreter versions.

## 7. Dependency Validation

After dependency installation, verify that the environment is usable.

### 7.1 Verify Python interpreter

Check the interpreter used by the project.

Windows:

```powershell
.venv\Scripts\python.exe --version
```

macOS / Linux:

```bash
.venv/bin/python --version
```

### 7.2 Verify installed dependencies

For uv-managed projects:

```bash
uv sync
uv pip list
```

For requirements-based projects:

```bash
uv pip list
```

Check that the required dependencies are installed.

### 7.3 Verify dependency consistency

For uv-managed projects:

```bash
uv lock --check
```

This checks whether the lockfile is consistent with the project configuration.

Do not run upgrade commands as part of routine validation.

### 7.4 Import validation

When appropriate, verify that critical packages can be imported.

Example:

```bash
uv run python -c "import requests; print('requests import successful')"
```

Only validate packages that are relevant to the project.

Do not assume that successful installation guarantees that the application itself works.

Application-level validation belongs to the Project Validation stage.

---

## 8. Error Handling

If dependency setup fails:

1. Capture the complete error message.
2. Identify whether the failure is related to:
   - Python version compatibility.
   - Dependency version conflicts.
   - Missing system libraries.
   - Network or package registry access.
   - Invalid dependency declarations.
   - Unsupported operating system or architecture.
   - Corrupted or incompatible virtual environment.
3. Determine whether a minimal, safe correction is possible.
4. Avoid changing unrelated dependencies.
5. Do not bypass dependency constraints simply to make installation succeed.
6. Report unresolved issues and request user input when necessary.

Do not repeatedly retry the same failed installation command without changing the underlying cause.

---

## 9. Completion Criteria

Dependency Setup is complete when:

- [ ] The authoritative dependency source has been identified.
- [ ] The correct project environment has been selected.
- [ ] Dependencies have been synchronized or installed successfully.
- [ ] Existing dependency declarations have been preserved.
- [ ] The lockfile is consistent when applicable.
- [ ] Critical dependencies can be imported.
- [ ] No unintended global package installation occurred.
- [ ] No unnecessary dependency upgrades or removals were performed.

## 11. Handoff

After completing Dependency Setup:

1. Preserve the final dependency configuration.
2. Report any unresolved dependency issues.
3. Do not start modifying application code.
4. Hand off to `project-validation.md`.

The next stage is responsible for validating the project structure, execution, and essential functionality.
